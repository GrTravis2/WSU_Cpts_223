## Comparison of sorting algorithms
After running the tests, quick sort was by far the fastest algorithm with an average sorting time of 1.1775 ms. The next fastest sorting algorithm was surprisingly shell sort at 3.0848 ms, this was only after landing on a final increment sequence. See Table 1 for more details on the increment sequences tested. Followed closely behind shell sort was heap sort at 3.6366 ms which was barely slower than shell sort, only by about half a millisecond. Trailing far behind the fastest three algorithms were insertion sort and shell sort variations with the early tested increment sequences. While the first few attempts are shell sort were somewhat in the ballpark of speed as heap sort, insertion sort was taking close to 80 ms to finish one trial! Another thing to note is that Insertion sort had the highest variation out of all the algorithms tested, as discussed in lecture, the speed of insertion sort is heavily dependent on how pre-sorted the data set is. Since we are dealing with a pseudo-random distribution of values across the data set, it makes sense that insertion sort would struggle to keep up with the other algorithms! In a real life situation, I expect that insertion sort would perform slightly better when compared to the other algorithms since data sets tend to have some level of order. However, with a random dataset the other algorithms had a large advantage. Both quick sort and heap sort had relatively low standard deviations of 0.0241 ms and 0.0581 ms respectively. Insertion sort and by extension shell sort had relatively higher variations with standard deviations of 0.6551 and 0.1194 respectively.

## Why quicksort finishes the fastest
The quick sort algorithm has a few advantages when compared to the other algorithms tested. When compared to heap sort, quick sort has the advantage of being in place, this saves time in copying over data and also the memory space needed to hold the copies of the data! Additionally, algorithms like insertions sort and shell sort require comparing potentially all values against each other, while quick sort only has to find the correct place for one value (the pivot) before repeating the process on a subset of the data set. Eventually this requires less comparisons and still guarantees the data will be sorted. Another thing to note is that quick sort is selecting the pivot based on random generated index in the range of the dataset, compared to insertion and shell sort this is an advantage as the dataset being random does not impact the performance of the algorithm. In fact you could argue that picking a random index on a randomly generated set of data is better than picking a random index on sorted data. All in all, quick sort is just as likely to find a balanced pivot by picking a random index given a random set of data.

## More on shell sort increment sequences
The increment sequence used for shell sort plays a large role in the performance of the algorithm. When developing the shell sort, I defaulted to the sequence used in class of n = 7, 5, 3, 1 which resulted in an average sorting time of about 13 ms. When determining other increment sequences I decided to continue using prime numbers as the value of n for the nSort algorithm call. The idea being that if incrementing by a prime number you are less likely to sort the same indexes within the same pass of the algorithm, when using a composite number like an even number I believe you would continue to sort the same numbers together over and over again, missing some other indexes that get passed over! Changing the increment sequence to count down from the first 10 prime numbers with the exception of skipping 2 and landing on 1 for the final sort, the sorting time was reduced down to about 4 ms! Continuing this trend further, I used the first 20 prime numbers and again skipped 2 and used 1. The result was another reductin in processing time, finishing at about 3 ms on average which was good enough to beat out heap sort. I expect that if I contiued this pattern I would continue to see small increases in performance, but diminishing returns in that eventually the extra passes do not pre-sort the data much better to overcome the cost of making another nSort call. Overall, I was very surprised to see shell sort perform this well, but I do think that heap sort may be a better option since it is more resitant to variations in how the data is ordered. However, this is at the cost of more memory being used.
